## 核心心智習慣：【真實第一，拒絕推測】
* **數字或結果對不上時，直接寫「對不上」並附原始資料，嚴禁撰寫推測的解釋**。
* 任何未經查證的數據來源，不得自行腦補理由掩蓋分歧（例：17:25 未經查證前，嚴禁寫成「回收車 288號」）。

---

## 第一章：【真實資料實機驗收三原則】

1. **原始回應與截圖存證原則 (Raw Evidence Principle)**：
   * 凡是涉及外部真實 API、第三方即時資料庫或車聯網定位的驗收，戰報回報中**必須檢附官方原始回應（Raw XML / JSON 原始片段）或實機操作截圖**。
   * 嚴禁口頭聲稱或憑空臆測數字，嚴禁自行修正數字掩蓋資料分歧。

2. **模擬測試認知界限原則 (Simulation Boundary Principle)**：
   * 戴明的沙盒與 Mock 模擬測試（Node.js VM 沙盒、時間模擬器、虛擬座標注入）**只能證明程式代碼邏輯正確，不能證明外部真實資料正確**。

3. **「待實測」安燈門禁原則 (Pending-Live-Audit Gate)**：
   * 凡是尚未取得真實外部環境（如真實營運時段、真實車機連線）即時比對的項目，**一律嚴格標記為【🟡 待實測】，絕對禁止標記【🟢 PASS】或出綠燈單！**
   * 只有在目標時段（例如出勤時段 16:30～17:30）完成：
     1. 清運e點通官方 APP 當下介面
     2. 生活管家雷達卡片當下介面
     3. 官方 API / Worker 轉發之原始 XML 節點
     三者實測完全一致時，方可正式轉為【🟢 PASS】結案出廠。

## 第二章：【回報誠信與交付門禁三鐵律 (Delivery Gate Rules)】

> 程式檢查工具：`check_delivery_gate.py`（或 `bionic_core/delivery_gate.py`），回報前必須 Exit Code 0。

1. **規則 1：【數字由程式計算輸出律】**：
   * 回報中的所有統計數字（幾條路線、幾項任務、幾站、已查證/未查證數）**一律由腳本計算後貼上，不得手打**。
   * 杜絕大腦憑空估算或手誤寫錯（如 18 條寫成 19 條）。

2. **規則 2：【派工單對照表與實體驗收律】**：
   * 回報結尾**必須檢附「派工單對照表」**，格式固定為：
     `| 項目 | 狀態（完成／未做／待實測） | 證據 |`
   * 檢查程式強制檢驗：凡標記為「完成」之項目，其列出之證據檔案路徑或 Git Commit Hash **必須物理存在於磁碟或倉庫中**，檔案不存在直接紅字報錯。

3. **規則 3：【資料變更與版本號連動律（區分不適用與無法檢查）】**：
   * 專案若無 `data/` 目錄或入口檔無版本變數，輸出「ℹ️ 規則 3 不適用」並安全通過。
   * 專案若具備 `data/` 與版本變數，但取不到 `git diff`，明確輸出「無法檢查」並判定失敗，絕不靜默放行。
   * 若變更 `data/` 目錄，`index.html` 中的 `DATA_VERSION` **必須在同一 commit 中同步變更**。

4. **雙重門禁分工原則（不重疊鐵律）**：
   * `evidence_gate.py`：管「心智學習入帳（tick）」，查真實網頁 URL 與逐字原文。
   * `delivery_gate.py`：管「任務交付結案（job delivery）」，查派工單證據檔案與版本號。
   * 學習自動跑 evidence_gate，交件手動跑 delivery_gate，互不重疊干擾。

---

## 第三章：【極簡回報格式規範】
* 回報嚴禁任何鋪張修飾性辭藻，結構嚴格限縮為三段：
  1. **做了什麼**
  2. **證據在哪**（檔案路徑 / Commit SHA / 原始資料）
  3. **還沒做什麼**（待實測 / 未做清單）
  4. 結尾附 **派工單對照表**。
